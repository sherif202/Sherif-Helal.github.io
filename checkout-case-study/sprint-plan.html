Why the biggest-impact story ships last. S2 (real total) is a Must, but ICE gave it the least evidence. Sprint 1 collects data (T2) and tests a prototype with buyers (T3), sprints 2 and 3 leave time to design it properly, and sprint 3 builds it with an A/B test (T4). If the tests say it matters less, S2 shrinks to the no-fee default and frees points. That is Gilad's step-projects idea inside a Scrum plan.

Dependencies

Read it as "must finish before"
  • S8 → S5: admin content before the buyer-facing trust content.
  • T1 → S6: track steps before removing one, so we can see the change.
  • T2 → T3 → S2: evidence, then prototype test, then build.
  • S1 → S9: the thank-you page repeats the delivery date S1 creates.
  • S3 → S7: save-details only makes sense once guest is the main path.

Definition of Ready and Done

Ready before a story enters a sprint
  • Story written as "As…, I want…, so that…" with a named persona
  • Given/When/Then acceptance criteria agreed with the PM
  • Linked evidence (E-ID) and the metric it should move
  • Designs or copy ready (mock-up for UI stories)
  • Components known from the backend view and dependencies cleared
  • Estimated by the team; fits in one sprint (≤ 8 points)
Done before a story counts
  • All acceptance criteria pass, checked by QA
  • Works on desktop and phone; no placeholder text on touched pages
  • Tracking event fires for the step it changes
  • Code reviewed and merged; no new high bugs
  • Admin text editable without a developer where it applies
  • PM accepted it in the sprint review; release note line written

Risks and fallbacks

Risk
T2 or T3 shows the real total doesn't matter
S2 shrinks to the no-fee default and the named fee (3 pts); S9/S7 move up.
Risk
Delivery rules per area take longer (S1)
Ship "Arrives by <date>" first, countdown later (S1 is negotiable).
Risk
Holiday week at the end of December
S7 and S9 are Could: they are the buffer and drop first.
Risk
No traffic for an A/B test
Use before/after on the funnel baseline from T1 instead.
Where I'd adjust your model. A sprint plan is a forecast, not a promise. Commit to the sprint goals, not to every story: if sprint 1 shows that velocity is 12, not 16, the Coulds drop and the goals stay. And each sprint ends by checking its metric, so the plan learns as it goes.
