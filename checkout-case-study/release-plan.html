Release plan v2.0 · "Trusted checkout"

The sprint plan ships as three small releases, one after each sprint, each behind a feature flag and rolled out in stages. Each release names its metric, its guardrails and when to roll back. Dates and targets are examples.

Deploy is not release. The technical release puts the code on production with the flag off; the business release turns it on for people. Splitting them means a deploy problem never reaches Nour, and the go-live day is a switch, not a scramble.

Go / no-go checklist

  • ☐ All stories in the release meet the Definition of Done
  • ☐ Tracking events checked in the funnel (T1) before the flag turns on
  • ☐ Release notes and support briefing ready
  • ☐ Rollback tested: switching the flag off restores the old flow
  • ☐ No open high-severity bugs on checkout
  • ☐ PM, dev lead and QA say go

Hypercare: the first 3 days after each business release

Who
One developer on call, QA and the PO; support reports straight to them.
What
Guardrails checked twice a day; each stage change (10% → 50% → 100%) needs a green check.
Exit
3 quiet days at 100% → normal support. A problem → rollback rule, or a hotfix release.

Things to keep in mind

  • Scope can change: keep a release backlog. A story added after "last day to add stories" waits for the next release unless the PO swaps out an equal-sized one.
  • Dependencies (S8 → S5, T3 → S2) can move a date: check them at every refinement.
  • Staging, test data and the flag setup are release work too: they are in the Definition of Ready and the go/no-go checklist.
  • Not every story must ship: S7 and S9 can move to v2.4 without breaking the v2.3 goal.
  • When a date slips, tell support, admins and finance the same day.

Where I'd adjust your model. A release plan is mostly a plan for being wrong safely. Feature flags, stages and rollback triggers mean a bad idea costs a few days with 10% of visitors, not a month with everyone. Write the rollback rule before launch, while nobody is attached to the feature. The release-management sheet assumes one big release with 4–6 weeks of lead time; with small releases every sprint, the same milestones shrink into days, which is why they are tied to the sprint calendar here.
