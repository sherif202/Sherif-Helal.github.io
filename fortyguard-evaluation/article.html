What I planned, and why

Each product goal became a claim to check in step 2.

Philosophy, all three productsTest from raw data to the finished screen, and keep a log row for every claim. I started with the most direct route to the numbers, then used it to judge each layer added on top. Each claim got an ID, a screenshot or a response, a severity and a fix.
Dashboard
API
MCP (AI assistant)
Strategy
Use it as a first-time user would. Compare every number on screen with the API, so any gap counts as a dashboard problem.
Treat it as the ground truth. Note the credits before and after every call, and send it bad input on purpose.
Ask in plain language, then check each answer against the API value. Use edge prompts to see if it makes things up.

What the hackathon teams' behaviour already shows

From 18 recorded team demos built on FortyGuard's API before my testing

They didn't fully trust the API
One team fell back to Open-Meteo and another put a caching gateway in front of FortyGuard. Customers protect themselves when a single dependency feels risky.
They wanted AI, but nobody used the MCP
14 of 18 teams added an AI layer and 5 built agents, yet none used the MCP. 8 said "the engine decides, the AI explains". That is exactly what the MCP does well today.
They misread the data
4 teams called the 2 m air temperature "surface" or "sensor" temperature, one of them inside an automated safety call. Results that describe themselves would prevent this.

Reliability, scalability and maintainability

FortyGuard is a data-intensive application: its hard problems are the amount, the complexity and the freshness of its data, not computing power. Martin Kleppmann's Designing Data-Intensive Applications (chapter 1) judges such systems on three properties. This is how FortyGuard measures up.

The book asksWhat I saw at FortyGuardWhat to do or measure
Reliability: keeps working correctly, even when things go wrong
Does a fault turn into a failure the user sees?Good The engine stayed consistent: the same 16.11 °C everywhere, and bad input rejected for free.
Weak The dashboard shows correct data so that it looks wrong.		Check data before it is displayed; the display is part of the system.
Can one fault spread everywhere?Weak On 18 Nov about 20 incidents hit every product at the same moment. The dashboard and the MCP both sit on one API.Isolate products; degrade gracefully, for example by serving cached maps.
Do people get clear monitoring and quick recovery?Weak A status page with a 39-day stale incident, progress stuck at 30%, no Cancel, and keys that can't be rotated.Honest telemetry; undo and cancel; rotatable keys.
Scalability: copes as load grows
What are the load parameters?300 requests a minute, a 50 mi² area cap, 30 heatmaps a day, 1M credits. Peak load is a heat wave, not an average day.Plan capacity for heat-wave peaks, not monthly averages.
How is performance described?Gap Only ranges exist: API 0.4–3.2 s, assistant 14–50 s, jobs 16 s to over 2 min. There are no percentiles, so the slowest users stay invisible.Track p50, p95 and p99 per product, and publish targets.
Is there a service target?Weak 98.28–99.14% uptime per service, against the common 99.9%.Set and publish an availability target.
Maintainability: easy to run, simple, and easy to change
Operability: can the team and customers see what's happening?Weak No time zone on results, a wrong status page, and an undated changelog.Results that describe themselves; a status page driven by real checks.
Simplicity: is there accidental complexity?Weak Limits written in four places, two billing systems, units that ignore Settings, seven forced tours.One source of truth; one billing model visible everywhere.
Evolvability: can it change safely?Weak 20 m was dropped in code but is still advertised; 13 contradictions built up.Generate docs, errors and MCP descriptions from one place.
5

Reliability and maintainability: root causes

Most of what I logged traces back to one of four causes.

Reliability means "will it give the same right answer every time, and tell me when it can't?" The engine passed every check I gave it. The surfaces didn't: the progress bar, the gallery and the status page each showed a state that wasn't true (R3).
Maintainability means "can the team change one thing without four places drifting?" Today a limit lives in docs, API errors, MCP descriptions and the dashboard separately, which is how 13 contradictions appeared (R1).

A product idea: rings for the reports customers generate

Turn the five tabs of a Heat Intelligence report into five rings around the headline number. Customers see the whole report at once and know what they haven't read yet.

Concept sketch drawn by me, not a FortyGuard screen. Section text is from the Marina del Rey report I generated.

How the five rings connect, from the ground up

The rings are layers. Geographic is the ground, the weather sits over it, buildings change it, events decide when it matters, and people add heat on top. Each ring is fed by FortyGuard data and should show up in the analytics customers already use.

The first three layers are well fed and visible in the analytics. Events is half there. Anthropogenic has no stated source and no analytics view, and it is the tab the report cuts off. Data sources come from FortyGuard's materials, weak links from my tests, and the ring-to-user mapping is my own reading.

One ring per tab
Geographic, Environmental, Urban factors, Events and Anthropogenic. Tap a ring or row to open that tab.
Rings fill as you read
Like closing a fitness ring. Whoever forwards the report can see whether all five parts have been read.
Each row leads with its finding
One line per tab, so the 16,000-word report finally gets a summary (Fig. 8).

The same rings fix the frozen progress bar

During generation each section fills on its own, in place of one bar stuck at 30% (Fig. 4).

What the evidence supports

  • The MCP worked first time. Its numbers were identical to the API's, it checked the cost before paid calls, and it didn't make up answers (M-01 to M-13).
  • The model gave one value (16.11 °C) for one tile and hour in the API, the dashboard and the PDF. I checked this for only one tile, so it is a single match, not a rate (Fig. 9).
  • The API is usable: async jobs, rate-limit headers, exact billing, and no charge for any of the 15 bad requests. Two of those returned a 500 instead of a clear error (E-05).
  • The dashboard is where it breaks down. 21 of the 32 High and Critical findings are there, mostly in how numbers are drawn, labelled and reported (Fig. 1, Fig. 2, Fig. 4, Fig. 7).
  • Limits, plans and keys are written separately in four places, and they drift apart (R1, Fig. 6).
